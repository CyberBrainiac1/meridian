# Meridian pitch video

Everything that makes the 29-second product demo lives in this directory.
Remotion project, source clips, score, renders.

```bash
cd video
npm install
npm run render      # -> out/meridian-demo.mp4  (1920x1080, 30fps, 870 frames)
npm run dev         # Remotion Studio, for scrubbing while you edit
npm run lint        # eslint + tsc
```

## Layout

| Path | What it is | In git? |
|---|---|---|
| `src/Composition.tsx` | The whole video. Seven beats, one file. | yes |
| `src/Root.tsx` | Registers the composition, holds `durationInFrames` (870). | yes |
| `public/fall.mp4` | Render input. 291 frames: the 211 live frames plus 80 held so the pose has somewhere to settle. | yes |
| `public/skeleton.mp4` | Render input. Real YOLO11 pose output over `fall.mp4`, generated by `tools/render_skeleton_video.py`. | yes |
| `public/music.mp3` | The score. **Not committed** — see below. | no |
| `assets/source/fall-v1-pixverse-211f.mp4` | The original PixVerse generation, before the tail was held. | yes |
| `assets/source/skeleton-v1-211f.mp4` | Its matching skeleton pass. Superseded, kept for provenance. | yes |
| `out/` | Renders. Reproducible from source, so ignored. | no |

## Why the clips are committed even though the repo ignores `*.mp4`

`fall.mp4` came out of a **one-shot PixVerse generation**. Generative video is
not deterministic: re-running the same prompt returns different footage, with a
different fall at a different moment. Every skeleton clip is derived from it,
and the composition's timings (`CLIP_START = 58`, impact at beat-frame ~85) are
tuned to that specific footage.

If these files are lost, the video cannot be rebuilt — only replaced with a
different one. That is why `video/.gitignore` re-includes them.

## The score is deliberately absent

`public/music.mp3` is AKTASOK's "Hopeful Ambient Background" under the
[Pixabay Content License](https://pixabay.com/music/corporate-hopeful-ambient-background-180353/):
free to use commercially, no attribution required, but redistributing the file
itself from a public repository is not what that licence is for. Re-download it
to `public/music.mp3` before rendering. Without it the render still completes;
it is simply silent.

## Regenerating the skeleton pass

If `fall.mp4` is ever re-cut, the skeleton must be regenerated from it or the
two layers will drift apart on screen — they share one scale ramp and are
composited with `mixBlendMode: screen`, so any mismatch is visible:

```bash
python tools/render_skeleton_video.py --source video/public/fall.mp4 \
  --out video/public/skeleton.mp4 --width 1920 --height 1080
```

This runs the real ONNX model. The skeleton in the video is genuine detector
output, not an illustration, and it must stay that way — see
`docs/pitch-video-plan.md` §0.

## Rules that are easy to break by accident

1. **870 frames exactly.** `Root.tsx` and the `T` cut map in `Composition.tsx`
   must agree.
2. **No digits on screen except "Room 101".** Metrics belong on deck slides
   where they can be sourced; the video only has to show the product working.
3. **Inline SVG for every icon.** Decorative Unicode font-falls-back in
   headless Chromium — U+2659 once rendered as a literal white chess pawn in
   the Residents tab.
4. **No hyphens or dashes in on-screen copy.**
5. After any change, re-render and check frame count and flash frames; the
   protocol is at the bottom of `docs/pitch-video-script.md`.
